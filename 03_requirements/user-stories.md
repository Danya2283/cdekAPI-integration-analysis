# User Stories с Acceptance Criteria

## US-01 — Расчёт стоимости и срока доставки

Как клиент, я хочу видеть стоимость и срок доставки до подтверждения заказа,
чтобы принять осознанное решение о покупке.

**Сценарий 1 — адрес покрыт доставкой:**
- Given: клиент ввёл корректный адрес доставки
- When: система отправляет запрос к API СДЭК
- Then: клиенту отображается стоимость и диапазон дат в течение 3 секунд

**Сценарий 2 — адрес не покрыт:**
- Given: клиент ввёл адрес вне зоны покрытия
- When: система получает ответ от API СДЭК
- Then: клиенту отображается сообщение «Курьерская доставка недоступна»

---

## US-02 — Оформление заказа с доставкой

Как клиент, я хочу оформить заказ с доставкой курьером,
чтобы получить товар без визита в пункт выдачи.

**Сценарий 1 — успешное оформление:**
- Given: клиент заполнил все поля и выбрал доставку курьером
- When: клиент подтверждает заказ и оплачивает
- Then: в системе СДЭК создаётся отправление, клиент получает email
с трек-номером в течение 1 минуты

**Сценарий 2 — API СДЭК недоступно:**
- Given: клиент оформил и оплатил заказ
- When: API СДЭК не отвечает
- Then: заказ фиксируется в системе магазина, отправление создаётся
автоматически после восстановления связи — не позднее чем через 1 час

---

## US-03 — Отслеживание статуса доставки

Как клиент, я хочу видеть актуальный статус своего заказа в личном кабинете,
чтобы знать когда ожидать курьера.

**Сценарий 1 — статус обновился:**
- Given: СДЭК изменил статус отправления
- When: система получает webhook-уведомление
- Then: статус в личном кабинете обновляется в течение 5 минут,
клиент получает push или email уведомление

**Сценарий 2 — заказ не вручён:**
- Given: курьер не смог вручить заказ
- When: СДЭК присваивает статус NOT_DELIVERED
- Then: клиент получает уведомление с причиной и инструкцией,
менеджер получает алерт в CRM

---

## US-04 — Контроль нештатных ситуаций

Как менеджер, я хочу получать алерты по заказам которые не удалось
передать в СДЭК автоматически, чтобы обработать их вручную и не потерять.

**Сценарий 1 — исчерпаны попытки retry:**
- Given: система трижды пыталась создать отправление и получила ошибку
- When: последняя попытка завершилась неудачей
- Then: менеджер получает уведомление с номером заказа и контактом клиента
в течение 5 минут

**Сценарий 2 — ручная обработка:**
- Given: менеджер получил алерт по заказу
- When: менеджер вручную создаёт отправление и вводит трек-номер в CRM
- Then: заказ переходит в штатный статус, клиент получает уведомление

---

## US-05 — Просмотр статусов всех отправлений

Как менеджер, я хочу видеть актуальные статусы всех активных отправлений
в одном месте, чтобы контролировать процесс без входа в личный кабинет СДЭК.

**Сценарий:**
- Given: менеджер открывает раздел «Доставки» в CRM
- When: страница загружается
- Then: отображается список активных отправлений с фильтрами по статусу,
дате и наличию проблем; данные актуальны на момент последнего webhook

---

## US-06 — Защита от дублирования отправлений

Как разработчик, я хочу использовать idempotency key при запросах к API СДЭК,
чтобы повторные запросы не создавали дублирующие отправления.

**Сценарий:**
- Given: запрос на создание отправления был отправлен, но ответ не получен
- When: система повторяет запрос с тем же order_uuid
- Then: API СДЭК возвращает данные уже созданного отправления
без создания нового

---

## US-07 — Верификация входящих webhook-уведомлений

Как разработчик, я хочу верифицировать подпись входящих webhook-запросов,
чтобы исключить обработку поддельных уведомлений.

**Сценарий:**
- Given: на эндпоинт магазина поступил POST-запрос
- When: система проверяет подпись запроса
- Then: запросы с невалидной подписью отклоняются с кодом 401,
валидные запросы обрабатываются в штатном режиме
